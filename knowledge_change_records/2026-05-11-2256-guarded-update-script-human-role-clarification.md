# 受控更新脚本与人工角色说明补充记录

## 1. 修改概述

本次对中文汇报文档补充说明：完整更新流程并不要求每次都新建一个具体更新脚本，同时解释为什么文档中仍然保留“人工或 LLM Agent 操作”的表述。

修改文件：

- `ai-/knowledge/llm_wiki_swine_authoritative/WIKI_GUARDED_UPDATE_EXECUTION_FLOW_CN.md`

新增章节：

- `3B. 是否每次都必须新建一个具体更新脚本`

## 2. 修改前存在的问题

原文档使用 `<具体更新脚本>.py` 描述实际数据写入命令，容易被理解为：

- 每一次完整流程都必须新建一个 Python 脚本。
- 更新过程仍然依赖大量人工操作。
- 固定入口似乎只适用于一次性专题脚本。

这些理解不够准确。

## 3. 本次新增内容

新增章节明确说明：

- 每次更新必须提供一条可执行更新命令，但不一定必须新建 `.py` 文件。
- 更新命令可以是新建脚本、已有脚本、通用参数化脚本、Python module 调用，或通用 updater 加数据补丁文件。
- `run_guarded_wiki_update.py` 的实际约束是接收并执行 `args.command`。
- DIS-026 示例采用一次性专题脚本，是为了增强审计可读性，不是固定入口强制要求。
- 后续可以建设 `apply_wiki_data_patch.py --patch <patch>.json` 这类通用更新器，减少重复脚本。
- 文档中的“人工或 LLM Agent 操作”主要指业务治理判断和留痕，不是指门禁、执行、验收需要手动完成。

## 4. 修改后解决的问题

修改后，文档可以更准确地说明当前自动化边界：

- 已自动化：治理门禁、CRUD 检查、更新命令执行、更新后验收、运行证据输出。
- 未完全自动化：来源权威性判断、CRUD 决策理由、旧数据处理策略、更新内容组织、工作汇报记录。

这可以避免汇报中被误解为“每次都要手工写脚本”或“流程没有自动化支撑”。

## 5. 预计效果

该补充有助于向评审或管理人员说明：

> 当前机制强调的是受控执行和可追溯，不是强制每次新建脚本。对于一次性专题更新，可以新建脚本；对于高频稳定更新，可以复用通用更新器。人工或 LLM Agent 参与的是判断和说明，代码负责门禁、执行、验收和证据。
