# 猪病 LLM Wiki 数据生成约束弱化与真实问诊 SFT 数据提升实施方案

## 一、方案目标

当前数据生成与评估系统已经具备 wiki 证据检索、样本规划、答案骨架、真实模型生成、事实门控、双裁判评估、仲裁和 CSV 导出能力。但当前生成结果仍偏“wiki 证据边界问答”，真实问诊场景不足，回答容易过度保守或机械堆叠引用。

本方案目标是在不牺牲安全性和可追溯性的前提下，适度弱化生成约束，充分利用现有数据，优先产出更有效、更多样化、真实感更强、可用于兽医问诊 agent 微调训练的 CSV 问答数据。

核心原则：

- 场景可以合成，疾病知识不能无依据合成。
- 主训练回答追求真实问诊可用性，审计字段保留 wiki 证据约束。
- 允许问诊建议、信息补充建议、检测核对建议，禁止无来源处方、剂量、休药期、监管执行结论。
- 先提高现有数据可用性，再逐步补充更多症状、病程、剖检、检测、鉴别和防控事实。

## 二、当前问题

### 2.1 生成结果过于像证据摘要

当前 `clinical_answer` 已经比原来的 `stage_2_grounded.answer` 更自然，但在证据不足的疾病上，仍容易出现“依据当前证据、不能直接扩展、引用锚点”的审计式表达。

原因：

- Phase14 prompt 强调 evidence anchors 和 citation。
- Phase15/Phase18 评分更看重引用完整和边界控制。
- 训练主回答和审计回答虽然已经分开，但裁判仍会受到 wiki-first 约束传统影响。

影响：

- 训练样本不像真实养殖户问诊。
- 对大模型微调的帮助偏向“保守拒答”，不足以训练问诊 agent 的有效回应能力。

### 2.2 真实病例场景变量不足

当前 wiki 中大量疾病事实仍停留在类别、教材页码、少量权威事实层面，缺少完整临床信息。

缺少的高价值变量包括：

- 日龄或生产阶段。
- 发病比例、死亡率、病程。
- 采食、精神、体温、呼吸、腹泻、神经症状等现场表现。
- 免疫史、用药史、引种和环境变化。
- 剖检变化、采样和实验室检测。
- 鉴别诊断和防控措施。

影响：

- 如果严格要求所有内容都有 wiki anchors，就只能生成很薄的回答。
- 如果完全放开，又可能出现模型杜撰疾病事实。

### 2.3 Hard gate 对问诊建议识别过严

当前规则会把部分“建议补充检测、建议核对病程、建议采样”等表达误识别为执行性风险。

影响：

- 合理问诊建议被误拒。
- accepted 样本比例偏低。
- 生成模型为了避免被拒，会倾向于少说、保守说。

### 2.4 裁判目标仍偏审计

Phase18 已经接入真实 LLM 双裁判和仲裁，但评分体系仍较重视 citation integrity、unsupported expansion control 和 safety boundary。

影响：

- 回答越自然、越像真实问诊，越可能因为没有每句话引用而被降分。
- 训练价值和问诊有效性没有被提升到足够高的权重。

## 三、总体设计

采用“双层样本结构”：

### 3.1 主训练层

字段：

- `case_context`
- `case_user_query`
- `assistant_answer`

用途：

- 作为 SFT / 微调主数据。
- 模拟真实养殖户提出具体问题。
- 兽医问诊 agent 给出自然、专业、有效、有边界的回答。

### 3.2 证据审计层

字段：

- `grounded_audit_answer`
- `evidence_anchors`
- `source_trust`
- `evidence_coverage`
- `phase15_*`
- `phase18_*`
- `judge_a_*`
- `judge_b_*`
- `arbiter_*`

用途：

- 证明回答不是完全自由生成。
- 追踪疾病知识结论来源。
- 支持质量审查、仲裁和人工复核。

为什么这样能解决问题：

- 主训练层不再被证据串格式绑死，可以提升真实感和训练价值。
- 审计层仍保留证据链，避免数据不可控。
- 场景变量和疾病知识可以分层管理，既增强多样性，又防止杜撰。

## 四、实施步骤

## 步骤一：建立通用猪场问诊场景变量库

### 修改内容

新增或扩展一个场景变量配置模块，例如：

- `tools/pipeline/consultation_case_variables.py`

包含通用、非疾病特异性的变量：

- 猪群阶段：保育猪、育肥猪、母猪、哺乳仔猪、断奶仔猪。
- 场景规模：小规模猪场、规模化猪场、家庭农场、育肥场、母猪场。
- 时间线：昨天开始、近 3 天、近 1 周、转群后、引种后。
- 现场表现：采食下降、精神变差、腹泻、咳嗽、发热、扎堆、死亡增加。
- 信息缺口：未检测、未剖检、免疫史不完整、用药史不清楚。
- 用户诉求：想初步判断、想知道是否需要检测、想知道能否用药、想知道能否调运、想知道防控边界。

### 理由

当前 wiki 临床事实不足，不能直接生成丰富病例。但真实问诊训练需要场景输入。通用变量不声明“某病必然有什么症状”，只模拟用户提供的信息，因此风险可控。

### 解决的问题

- 解决 `case_user_query` 过于模板化的问题。
- 提升问答多样性和真实感。
- 让训练样本更接近兽医 agent 的实际使用场景。

### 为什么能解决

因为问诊场景的真实感主要来自用户输入的背景信息，而不一定来自疾病知识本身。只要明确这些背景是“用户描述”，不是“疾病事实”，就可以在不扩展疾病知识的情况下提高样本可用性。

### 风险控制

- 场景变量标记为 `synthetic_case_context`。
- 不允许模型把场景症状写成“该病典型症状”。
- 裁判检查回答是否错误绑定症状和目标疾病。

## 步骤二：改造 Phase13 生成骨架

### 修改内容

在 `phase13_build_answer_skeletons.py` 中继续完善：

- `case_generation_profile`
- `clinical_answer_contract`

新增字段建议：

- `case_variable_policy`
- `allowed_synthetic_context_types`
- `forbidden_disease_specific_inference`
- `answer_quality_targets`
- `minimum_consultation_moves`

示例：

```json
{
  "case_variable_policy": {
    "allowed": ["日龄", "发病比例", "病程", "用户主诉", "检测缺失"],
    "forbidden": ["把合成症状说成该病典型症状", "生成无来源确诊", "生成无来源用药方案"]
  },
  "minimum_consultation_moves": [
    "回应用户主诉",
    "说明当前能判断什么",
    "说明不能直接判断什么",
    "提出需要补充的信息",
    "给出安全边界"
  ]
}
```

### 理由

Phase13 是生成链路的“骨架层”。如果骨架只提供事实 claim，Phase14 就只能围绕事实生成；如果骨架明确告诉下游“这是问诊 SFT 样本”，Phase14 才能稳定生成更像真实问诊的数据。

### 解决的问题

- 解决 prompt 单点控制不稳定的问题。
- 让每条样本自带生成契约。
- 提高不同能力层样本的一致性。

### 为什么能解决

因为骨架会进入后续 prompt、门控、裁判和导出链路。把质量要求前置到骨架，可以让生成和评估共享同一套样本目标，减少“生成想自然，评估按审计拒绝”的冲突。

## 步骤三：弱化 Phase14 对主回答的格式约束

### 修改内容

Phase14 中继续区分两个答案：

- `clinical_answer`：主训练答案。
- `stage_2_answer` 或 `grounded_audit_answer`：审计答案。

对 `clinical_answer` 弱化以下要求：

- 不要求每一段都按固定标签输出。
- 不要求每一句都带 citation。
- 不要求一开头就写“依据当前证据”。
- 不要求所有边界都机械展开。

保留以下硬要求：

- 疾病知识结论必须能回到 anchors。
- 文末或关键结论处必须保留证据锚点。
- 不得生成无来源确诊。
- 不得生成无来源药物剂量、疗程、休药期。
- 不得生成无来源监管动作。

### 理由

SFT 数据的主回答需要像真实兽医 agent，而不是审计报告。引用和边界是必要的，但不能破坏自然对话。

### 解决的问题

- 减少模板腔。
- 减少对象串和证据串。
- 提升回答可读性和微调价值。

### 为什么能解决

大模型微调学习的是输入输出形式。主回答越接近真实问诊 agent，训练效果越接近目标使用方式。审计信息保存在独立字段中，不需要挤压主回答。

## 步骤四：调整 Phase15 hard gate 白名单

### 修改内容

新增“允许的问诊建议”白名单：

- 建议补充日龄、批次、栏舍、发病比例。
- 建议记录死亡率、病程、采食、精神状态。
- 建议联系兽医采样。
- 建议做实验室检测。
- 建议核对免疫史、用药史、引种史。
- 建议隔离观察和加强常规生物安全。

仍禁止：

- 具体药物剂量。
- 具体疗程。
- 具体给药方式。
- 具体休药期或 MRL。
- 无官方来源的上报、扑杀、封锁、调运结论。

### 理由

问诊 agent 必须能够提出下一步信息收集建议。如果这些建议被误判为风险，模型就只能输出空泛保守话术。

### 解决的问题

- 减少合理问诊建议被拒。
- 提高 accepted 样本比例。
- 让回答更有帮助。

### 为什么能解决

检测建议和信息补充建议不是处方，也不是监管执行。把它们从高风险触发中区分出来，可以在安全边界内提升回答有效性。

## 步骤五：调整 Phase18 双裁判评分权重

### 修改内容

在裁判评分中提高以下维度权重：

- `question_resolution`
- `training_utility`
- `language_naturalness`
- `answer_completeness`

降低对主回答中逐句 citation 的强制依赖。

保留对以下风险的高权重惩罚：

- unsupported diagnosis。
- unsupported prescription。
- drug dose / withdrawal / MRL hallucination。
- regulatory action hallucination。
- 把合成病例变量当作疾病事实。

### 理由

当前裁判偏审计，导致自然问诊回答容易被 review。训练主数据需要更关注“是否可作为兽医 agent 高质量回答”。

### 解决的问题

- 减少高质量自然回答被降级。
- 提高 accepted 样本质量和数量。
- 让仲裁更贴合训练目标。

### 为什么能解决

裁判决定样本能否进入 train-ready。评分权重如果不改变，生成侧即使改好，也会被旧规则筛掉。评估目标必须和训练目标一致。

## 步骤六：新增样本分层策略

### 修改内容

将输出分为四类：

- `train_ready_consultation_sft`：可直接用于问诊 SFT。
- `train_ready_boundary_sft`：可用于安全边界训练。
- `review_consultation_repair`：问诊形式好但证据或安全边界需复核。
- `audit_or_rejected`：仅用于审计、反例或裁判校准。

### 理由

不是所有数据都应该进入同一个训练集。问诊样本、安全边界样本、反例样本有不同用途。

### 解决的问题

- 避免保守拒答样本污染主训练集。
- 保留 review/rejected 的利用价值。
- 方便后续人工复核和二次改写。

### 为什么能解决

分层后可以让主训练集更纯净，同时不浪费边界样本和反例样本。

## 步骤七：建立批次验收指标

每次真实生成后统计：

- 总样本数。
- accepted / review / rejected 分布。
- 平均回答长度。
- `case_user_query` 平均长度。
- `clinical_answer` 是否含真实问诊结构。
- 引用锚点完整率。
- 合成场景误绑定疾病事实数量。
- 药物/监管高风险错误数量。
- 主训练样本比例。

建议目标：

- accepted 比例：初期 35% 到 55%。
- review 比例：30% 到 45%。
- rejected 比例：控制在 10% 到 25%。
- 主训练样本平均回答长度：300 到 900 中文字符。
- `case_user_query` 至少包含 3 个场景变量。
- 高风险错误必须为 0。

### 理由

如果没有量化验收，无法判断“弱化约束”是提高可用性，还是引入风险。

### 解决的问题

- 让每次批量生成可评估。
- 便于向管理层汇报质量变化。
- 便于比较不同 prompt 和裁判配置。

### 为什么能解决

指标能够把生成质量从主观判断转成可追踪数据。后续每轮优化都能看到 accepted 比例、自然度和风险控制是否改善。

## 五、推荐实施顺序

### 第一阶段：低风险改造

修改内容：

- 增加通用病例变量库。
- Phase14 使用病例变量库构造更真实的 `case_context` 和 `case_user_query`。
- 主回答 citation 从“段段强制”改为“关键结论或文末保留”。

理由：

- 不触碰高风险药物和监管规则。
- 先提升问诊真实感。
- 失败风险低。

预计效果：

- 生成样本更像真实用户咨询。
- 回答更自然。
- review 样本中“语言机械”问题下降。

### 第二阶段：门控和裁判校准

修改内容：

- Phase15 加问诊建议白名单。
- Phase18 提高训练价值、问题解决、自然度评分权重。
- 仲裁增加“主训练可用性”判断。

理由：

- 生成侧优化必须和评估侧同步。
- 否则好样本仍会被旧规则打入 review。

预计效果：

- accepted 比例上升。
- 合理问诊建议不再被误拒。
- train-ready 数据更多。

### 第三阶段：批量重跑和质量分析

修改内容：

- 先跑 10 条真实模型验证。
- 再跑 40 条 8 路并发。
- 输出完整耗时、分布、质量报告。

理由：

- 小批次验证防止大批量浪费 API。
- 40 条可以观察 accepted/review/rejected 分布是否合理。

预计效果：

- 得到第一版更可用的真实问诊 SFT CSV。
- 明确后续知识库补充优先级。

### 第四阶段：逐步补充知识库深层事实

补充内容：

- 症状。
- 病程。
- 剖检。
- 检测。
- 鉴别诊断。
- 防控原则。
- 真实病例场景模板。

理由：

- 弱化约束能先提高可用性，但不能替代知识库建设。
- 深层事实越多，回答越能从“问诊建议”升级为“更完整临床支持”。

预计效果：

- 主训练样本更丰富。
- 高质量 accepted 样本比例进一步提升。
- 问诊 agent 的临床帮助性增强。

## 六、验收标准

本方案完成后，应满足：

- CSV 中 `case_context`、`case_user_query`、`assistant_answer` 均非空。
- `assistant_answer` 是自然兽医问诊回答，不是证据串。
- `grounded_audit_answer` 保留审计证据。
- Phase15 不再误拒普通问诊建议。
- Phase18 裁判围绕真实问诊回答评分。
- train-ready 主训练数据比例明显提升。
- 高风险错误为 0。
- 所有修改均有 `knowledge_change_records` 留痕。

## 七、风险与应对

### 风险一：模型把合成场景当作疾病事实

应对：

- 在 prompt 中明确合成场景只代表用户描述。
- Phase18 增加“synthetic context misuse”扣分。
- CSV 保留 `case_context.provenance`。

### 风险二：回答过度放开导致幻觉

应对：

- 疾病知识结论仍必须引用 anchors。
- 高风险药物和监管结论仍维持硬拒绝。
- review 队列保留人工复核入口。

### 风险三：accepted 比例上升但质量下降

应对：

- 使用批次指标监控。
- 抽检 accepted 样本。
- 对 accepted 样本增加最小信息密度和自然度要求。

### 风险四：历史数据兼容性问题

应对：

- 新字段采用兼容读取策略。
- 如果没有 `clinical_answer`，回退读取 `stage_2_grounded.answer`。
- 如果没有 `case_user_query`，回退读取 `question`。

## 八、结论

建议执行该方案。

当前主要矛盾不是系统无法生成数据，而是生成目标仍偏审计，导致现有数据没有被充分转化为真实问诊训练样本。通过适度弱化主回答格式约束、引入通用病例变量、区分主训练层与证据审计层、校准 hard gate 和双裁判，可以在不等待知识库完全补齐的情况下，先产出更加有效、多样化、真实感更强的 SFT 数据。

后续再逐步补充症状、病程、剖检、检测、鉴别、防控等知识库事实，可以进一步提升样本深度和临床帮助性。
