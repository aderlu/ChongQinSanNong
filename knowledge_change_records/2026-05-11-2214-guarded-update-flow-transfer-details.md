# 受控更新流程调用与流转细节补充记录

## 1. 修改概述

本次对中文汇报文档进行了增强，重点补充每一个环节如何调用下一个环节、数据和执行结果如何流转、失败时在哪里中断。

修改文件：

- `ai-/knowledge/llm_wiki_swine_authoritative/WIKI_GUARDED_UPDATE_EXECUTION_FLOW_CN.md`

新增章节：

- `3A. 逐环节调用与流转明细`

## 2. 修改前存在的问题

原中文文档已经说明了整体流程、职责分工、固定入口、门禁检查、更新后验收和证据文件，但对“环节之间如何衔接”的说明还不够细。

具体不足包括：

- 没有逐项说明上一个环节的输出如何成为下一个环节的输入。
- 没有明确 `--` 后面的更新命令如何进入 `args.command`。
- 没有明确 preflight 脚本是由 `PREFLIGHT` 列表统一调度。
- 没有明确具体更新脚本和 postcheck 之间是通过文件系统交接。
- 没有明确 postcheck 总入口如何继续调用各个验收子脚本。
- 没有明确失败时由哪个环节写入什么原因并中断。

## 3. 本次新增内容

新增的 `3A. 逐环节调用与流转明细` 章节包括：

- 从更新需求流转到 CRUD 决策。
- 从 CRUD 决策流转到固定入口命令。
- 固定入口如何调用更新前门禁。
- 治理检查如何流转到 CRUD 检查。
- 从更新前门禁流转到具体更新脚本。
- 具体更新脚本内部如何把数据落到 wiki。
- 从更新脚本流转到更新后验收。
- 更新后验收脚本如何调用各个子检查。
- 从图谱重建流转到图谱 diff。
- 从验收结果流转到固定入口运行报告。
- 从运行报告流转到人工工作留痕。

每个小节按以下格式说明：

- 输入。
- 执行动作。
- 输出。
- 流转到下一环节的方式。
- 失败时如何中断。

## 4. 修改后解决的问题

修改后，文档不仅能说明“有哪些流程”，还能说明“流程之间是怎么接起来的”。

现在可以清楚回答：

- CRUD 决策文件如何被后续检查读取。
- 固定入口如何接收并暂存具体更新命令。
- preflight 如何按顺序执行。
- 门禁为什么能阻止不合规更新脚本执行。
- 更新脚本落库后，postcheck 如何重新扫描文件并重建产物。
- 图谱重建结果如何进入 graph diff。
- 最终运行结果如何写入 JSON 和 JSONL 证据。
- 工作留痕如何接收机器证据并形成汇报材料。

## 5. 预计效果

该补充可以帮助汇报对象理解完整执行链路：

> 每个环节不是孤立存在的，而是通过固定目录、命令参数、子进程调用、文件系统落库、验收产物和运行报告逐步流转，最终形成可审计闭环。
