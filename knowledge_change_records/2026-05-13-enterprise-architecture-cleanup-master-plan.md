# 2026-05-13 企业级架构清洗总计划

## 本次背景

当前 `D:\XF-ChongQin\ai-` 项目已经同时承载了：

- 猪病 LLM Wiki 权威知识库运行时
- 基于知识库的数据生成、评估、仲裁工程
- 历史试运行脚本、阶段性方案文档、演示产物、问题记录、结果文件

随着功能增长，项目出现了“核心链路与历史沉积混杂”的问题，导致目录可读性下降、运行边界不清、交付汇报成本上升，也增加了后续企业级治理和交接难度。

本轮工作目标不是大规模推翻重建，而是在**不破坏当前主链运行能力**的前提下，分批完成一次企业级的结构清洗、归档治理和职责归位。

## 清洗前存在的问题

1. 根目录层面存在 `results/`、`exports/`、`issues/`、`knowledge_change_records/` 等不同性质内容并列堆放，产物、问题、文档和核心代码边界不清。
2. `docs/` 中既有当前仍需参考的架构文档，也有大量历史实施计划、演示稿、阶段性执行方案，缺乏归档分层。
3. `scripts/` 目录中混合了当前兼容入口脚本与带日期的一次性批处理脚本、回填脚本、试验脚本，不利于企业级运维管理。
4. `knowledge/llm_wiki_swine_authoritative/tools/` 中同时存在 Wiki 维护工具、运行审计工具、图谱工具、数据生成与评估工具，职责聚合度不足。
5. 项目内存在多处历史中文终端显示乱码的现象，如果在清洗过程中直接粗暴重写旧文档，可能进一步放大编码风险。
6. 当前仓库为脏工作区，存在用户已生成但未提交的运行产物与新链路脚本，清洗动作必须兼顾安全性和兼容性。

## 本轮总策略

### 一、先治理结构，再治理命名

本轮优先做：

- 归档目录建立
- 历史文档迁移
- 一次性脚本迁移
- 根目录历史产物归档
- 数据生成与评估工具链职责分组
- 核心说明文档重建

本轮暂不直接做：

- `src/chicken_data_synthesis` 包名整体重命名
- 大面积 Python import 路径破坏式调整
- 删除用户可能仍在使用的未跟踪运行产物

### 二、保留兼容入口

对于仍可能被测试、文档或人工命令直接引用的脚本路径，优先采用：

- 迁移到更合理目录
- 原路径保留兼容包装入口或索引说明

避免整理后出现“目录变整齐，但旧流程全部失效”的问题。

### 三、每批修改都留痕

所有实际动作均在 `D:\XF-ChongQin\knowledge_change_records` 下形成说明文档，方便后续：

- 工作汇报
- 审计复盘
- 阶段交付说明
- 团队接手

## 计划中的分批动作

### 第一批

- 建立企业级归档骨架
- 建立编码与留痕规范文档
- 迁移根目录历史运行产物
- 迁移 `docs/` 历史实施计划与演示文档
- 迁移 `scripts/` dated 一次性脚本
- 为 `tools/` 建立分层目录和索引

### 第二批

- 重组 `knowledge/llm_wiki_swine_authoritative/tools/` 中的数据生成、评估、仲裁代码
- 将 phase12/13/14/15/16/18 与客户端、评审 prompt 放入更明确位置
- 保留旧入口兼容文件或建立清晰重定向
- 补充工具链运行说明

### 第三批

- 清理仓库内重复或边界模糊的说明文档
- 对仍需保留的核心文档进行目录索引和职责说明
- 对结果目录、归档目录、输出目录建立长期治理规则

## 编码与乱码防护策略

本轮统一遵循以下原则：

1. 新增和重写文本文件统一使用 UTF-8。
2. 尽量避免直接重写历史中文大文档正文，优先迁移归档。
3. 读取 JSONL、Markdown、配置文件时优先使用 `utf-8` 或 `utf-8-sig` 兼容方式。
4. 说明文档统一使用纯文本 Markdown，不引入高风险格式转换。
5. 对核心入口文档采用“新建规范文档替代旧文档”的方式，降低历史编码污染传播风险。

## 预期效果

完成本轮整理后，项目会形成以下改善：

- 根目录更接近企业级仓库的清晰结构
- 历史文档、历史脚本、历史产物不再与核心主链混杂
- 猪病 Wiki-first 数据生成与评估链路的代码边界更清楚
- 后续排查真实 API、数据质量、评估仲裁链路时可读性明显提升
- 汇报材料和变更审计链条更加完整
- 后续再做包级重命名和正式模块化改造时风险更低
